# SalonOS — MVP ТЗ v1.0

> Каноническое техническое задание проекта. Если реализация расходится с этим документом, сначала сверяемся с ним и только после этого меняем код.

## 1. Цель
SalonOS — продаваемый multi-tenant SaaS/PWA для салонов красоты: публичная страница салона, онлайн-запись, управление мастерами, услугами, расписанием, клиентами и записями.

Критерий MVP: новый салон можно создать и настроить без изменения исходного кода, получить публичную ссылку, а реальный клиент с телефона может выбрать услугу → мастера → дату → свободное время → имя/телефон и создать запись. Администратор видит запись и может ей управлять.

## 2. Роли
- admin — полный доступ к своему салону.
- master — только разрешённые данные своего салона и собственные записи.
- superadmin — список салонов, просмотр, активация/деактивация.
Клиенту аккаунт не нужен.

## 3. Multi-tenant
Каждая бизнес-сущность принадлежит salon_id. Backend не принимает salon_id от клиента как источник прав: salon_id определяется сервером по авторизованной сессии. Нельзя получить данные другого салона подменой ID.

## 4. Onboarding
Регистрация администратора: имя, email/телефон, пароль, название салона. Затем быстрые шаги:
1) данные салона и логотип;
2) выбор темы;
3) мастера;
4) услуги;
5) услуги мастеров;
6) рабочее расписание;
7) готовая публичная ссылка.

После настройки салон должен работать без разработчика.

## 5. Четыре темы публичного салона
Один backend и одна система записи; меняется визуальная тема.
1. Light — светлый premium/minimal.
2. Dark — тёмный premium.
3. Soft — мягкий beauty-стиль.
4. Modern — современный выразительный универсальный стиль.
Выбор темы сохраняется и применяется после перезагрузки. Темы должны быть реально различимыми, а не только сменой одного цвета.

## 6. Брендинг
Настраиваемые поля: название, логотип, описание, телефон, адрес, акцентный цвет, тема, slug.

## 7. Публичная страница
URL формата /s/{slug}. Показывает логотип/название, описание, адрес/телефон, услуги, мастеров и кнопку онлайн-записи. Mobile-first + desktop.

## 8. Онлайн-запись
Шаги:
1) услуга;
2) мастер — только активные мастера, оказывающие услугу;
3) дата;
4) свободные слоты;
5) имя + телефон;
6) подтверждение с салоном, услугой, мастером, датой, временем и ценой.
Нельзя записаться в прошлое, вне графика, на выходной, на заблокированное время или на занятый слот.

## 9. Защита двойной записи
Проверка выполняется на backend и уровне БД/транзакции. Два одновременных запроса не должны создать конфликтующую запись одного мастера.

## 10. Мастера
Поля: имя, фото, описание, телефон (опционально), active. Администратор назначает мастеру услуги.

## 11. Услуги
Поля: название, описание, цена, длительность, active. CRUD/деактивация.

## 12. Расписание
Для каждого мастера: рабочие дни и время. Нужны исключения: выходной или блок времени на конкретную дату.

## 13. Записи
Администратор видит сегодня/завтра/календарь и фильтры по мастеру/статусу. Действия: изменить, отменить, завершить.
Статусы MVP: confirmed, completed, cancelled, no_show.

## 14. Клиенты
Автоматически создаются при первой записи. Хранятся имя, телефон, история записей. Без сложной CRM.

## 15. Уведомления
MVP: уведомление администратору о новой записи. Предусмотреть Telegram как первый канал, через настройки/переменные окружения. Архитектура должна позволять позже добавить SMS/WhatsApp/push.

## 16. Авторизация
Админ и мастер входят по email/телефону + пароль. Сессия хранится безопасно на сервере. Клиенту аккаунт не нужен.

## 17. Superadmin
Минимальная внутренняя панель: список салонов, открыть, активировать/деактивировать. Без сложной аналитики.

## 18. PWA
Установка на телефон через Add to Home Screen. Responsive: 360–430px mobile, tablet, 1280px+ desktop.

## 19. БД
Минимальные сущности:
salons, users, masters, services, master_services, clients, appointments, master_schedules, schedule_exceptions, salon_settings, sessions.
PostgreSQL — основная БД; SQLite допустим для локального запуска/демо.

## 20. Безопасность и целостность
- password hashing с солью;
- серверная авторизация;
- tenant isolation;
- проверка active/role;
- защита от двойной записи;
- валидация телефона, цены и длительности;
- нельзя удалить данные, нарушившие историю записей: для услуг/мастеров использовать деактивацию.

## 21. Не входит в MVP
AI, бухгалтерия, склад, зарплаты, сложная CRM, лояльность, бонусы, онлайн-оплата, нативные Android/iOS приложения, сложная аналитика, маркетинговая автоматизация, множество ролей, сложная биллинговая система.

## 22. Definition of Done
MVP готов, когда:
- можно зарегистрировать несколько независимых салонов;
- каждый салон настраивается без кода;
- работают все 4 темы;
- публичная страница доступна по slug;
- клиент создаёт реальную запись с телефона;
- свободные слоты рассчитываются по графику, исключениям и существующим записям;
- двойная запись невозможна;
- администратор видит и изменяет записи;
- клиентская запись создаёт/обновляет клиента;
- мастер видит только свои записи;
- tenant isolation проверен;
- PWA работает на mobile/desktop;
- локальный запуск документирован.

## 23. Принцип разработки
Не добавлять функции только ради «круто». Любая новая функция сначала проверяется против MVP: помогает ли она реальному салону принимать и управлять записями и продавать продукт. Если нет — в post-MVP.
